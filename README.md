# なし栞 + なしスタジオ

[![build](https://github.com/miyagawa-yukinterface/nashi-shiori-studio/actions/workflows/build.yml/badge.svg)](https://github.com/miyagawa-yukinterface/nashi-shiori-studio/actions/workflows/build.yml)

伺か（SSP）用の **栞（SHIORI）** と、その栞を使うゴーストを **Scratch のようにブロックを積んで作れるアプリ** の一式です。
どちらも Windows ネイティブ（C++ / MSVC）で、ランタイムのインストールは要りません。

| | |
|---|---|
| **なし栞 `nashi.dll`** | SHIORI/3.0 の DLL（32bit）。**SSP と同じく Windows 2000 から**動きます。会話は C++ ではなく `ghost.json` に入ったブロックで書く。 |
| **なしスタジオ `nashi-studio.exe`** | ブロックエディタ本体（64bit・単体で動く1ファイル）。自前のウィンドウに WebView2 を埋め込んだネイティブアプリ。UI も栞も exe の中。 |

---

## 動く環境

|  | |
|---|---|
| **書き出したゴースト**（`nashi.dll` が入ります） | **Windows 2000 以降**。SSP の動作環境に合わせてあります |
| **なしスタジオ**（`nashi-studio.exe`） | **Windows 10 / 11**（WebView2 が要ります） |

ゴーストを**作る**のは新しい Windows で、**配ったゴーストが動く**のは古い Windows から、
という形です。エディタは WebView2（Edge）の上に乗っているので、古い Windows では動きません。

栞のほうは、そこに合わせるために **Visual Studio の C ランタイムを使わずに**組んでいます。
ふつうに組むと、自分では呼んでいない Vista からの API が混ざってしまい、
そこから下の Windows では**読みこみ自体が失敗する**ためです。
ねらいどおりかは `node tools\check-imports.js` がいつでも確かめます
（くわしくは [`docs/maintenance.md`](docs/maintenance.md)）。

## つかいかた

### 1. 起動する

**`nashi-studio.exe` をダブルクリック** するだけです。
はじめてなら「開く」→「**お手本から始める**」で、動くゴーストを読みこんで
中を見るのがいちばん早いです（あいさつ／好感度／時間で変わる／名前をきく／ゴースト間通信）。

* 自分のウィンドウが開きます。ブラウザは起動しませんし、アドレスバーもタブもありません。
* ウィンドウを閉じればアプリも終わります。保存していない変更があれば確認します。
* ウィンドウの位置と大きさは次回起動時に復元します。
* 二重起動しても増えません（すでに開いているウィンドウが前に出ます）。

**ポートは開きません。** 画面からの要求は WebView2 の中で受け取って、そのまま exe の中で処理しています。
外に出る通信もしません（SSP と話すときだけ `127.0.0.1:9801` へ接続します）。

> 画面表示に **Microsoft Edge WebView2 ランタイム**（Windows 11 標準搭載）を使います。
> 万一入っていない場合は、起動時に案内と配布ページへのリンクを出します。

### 2. ブロックを組む

1. 左の **イベント** から「起動したとき」などをキャンバスにドラッグします。
2. その下に **セリフ** の「◯◯が □□ と話す」をつなげます。
3. 右の **ためす** タブの ▶ で、しゃべる様子とさくらスクリプトを確認できます。
   下に **いまの変数** が出ます。好感度などが変な値で固まったら「ここの変数をもどす」
   （エディタの中だけ）か「ゴーストの記憶を消す」（書き出したゴーストの `nashi_save.json`）
   でやり直せます。
4. 立ち絵は **ゴースト** タブの「立ち絵の画像」で、用意した PNG を番号ごとに割り当てられます
   （えらばなかった番号は、指定した色でかんたんな立ち絵を自動生成します）。
   同じタブの「**うごき**」で、立ち絵をパラパラ切りかえるアニメーションを作れます。
   「いつ動く」を決めておけば勝手に動きますし、「うごき N を再生する」ブロックでも呼べます。
   こまごとに重ねかたと位置を決められ、「そのうごきの間だけ触れる場所」も足せます。
5. **さがす** タブ（Ctrl+F）で、セリフや変数名からブロックを探せます。
   クリックするとその場所へ移動します。ブロックは **Ctrl+C / Ctrl+V** でコピーできます。
6. **チェック** タブに、空のセリフ・無い変数・行き先のない選択肢などが出ます。
   赤い数字が付いていたら、そこを直してから書き出してください。項目をクリックすると
   その場所までキャンバスが動いて、ブロックが光ります。

### 3. SSP に入れて動かす

**書き出し** タブの「**SSP に入れて動かす**」を押すだけです。

* SSP の場所（`ssp.exe`）を自動で探します。動いていれば実行中のプロセスから、
  止まっていれば `C:\ssp` などのよくある場所から見つけます。
  見つからないときは、同じ画面の欄に `ssp.exe` のパスを入れて「この場所を使う」。
* SSP の `ghost\` フォルダへ直接書き出し、そのまま **SSP のゴーストを切り替えます**。
* すでにそのゴーストが動いていた場合は、書き出したあと **栞だけ読み込み直します**（切り替え無し・一瞬）。
* SSP が止まっていれば「SSP を起動」で立ち上げられます。

配布用にまとめるときは、同じ画面の「.nar を作る」。
できた `.nar` を SSP のウィンドウにドラッグ＆ドロップするとインストールできます。

> SSP を動かしたまま書き出し直した場合、栞が数秒以内に `ghost.json` を読み直すので、
> 手動でのリロードも基本的に要りません。

### 4. 動いているゴーストで試す（SSTP 連携）

**ためす** タブに SSP の接続状態が出ます。つながっていれば:

* **SSPでしゃべらせる** — いま選んでいるトークを、**デスクトップで動いている本物のゴースト**に
  しゃべらせます（エディタ内のプレビューではなく実機確認）。
* **イベント送信** — 選んでいるイベント（`OnMouseDoubleClick` など）を SSP に投げて、
  入れたゴーストが実際にどう反応するかを確かめます。
* **話しかけてみる** — 他のゴーストのふりをして、動いているゴーストに話しかけます。
  「話しかけられたとき」のブロックを選んでいれば、その相手・内容で話しかけるので、
  しぼり込みが効いているかそのまま確かめられます。

内部では SSP の **SSTP**（`127.0.0.1:9801`）に `SEND` / `NOTIFY` / `EXECUTE` /
`COMMUNICATE` を送っています。
SSP 側で「SSTP を受け付ける」設定が有効（既定でオン）になっている必要があります。

絵を用意していない場合は、簡単な立ち絵（サーフェス 0/1/2 と 10/11/12）を自動生成します。
自分で描いた絵に差し替えるときは `shell/master/` の PNG を置き換えてください。
既にあるシェル画像は、書き出し直しても上書きされません。

**バルーン（吹き出し）**も、ゴーストタブの「バルーンも作る」を入れると同梱できます
（`balloon/` に PNG と `descript.txt` が入り、`install.txt` に置き場所が書かれます）。
入れないときは、使う人が持っているバルーンで表示されます。
こちらも自分で描いた PNG があれば、書き出し直しても上書きしません。

### 5. ネットワーク更新に対応する

配ったあとのゴーストを、こちらの直したものに追いつかせるしくみです。

1. **ゴースト** タブの「**更新のありか**」に、置き場所の URL を入れます
   （うしろに `/` を付けます。例: `https://example.com/ghost/nashiko/`）。
   ここが `descript.txt` の `homeurl` になります。空なら何も書かないので、更新もしません。
2. 書き出すと、フォルダに **`updates2.dau`**（中身の照合表）も一緒に作られます。
   使う人の SSP はこれを見て、**変わったファイルだけ**を落としてきます。
   自分で差し替えた絵やあとから足したファイルも、フォルダの中身から作るので入ります。
3. そのフォルダの中身を、URL の場所へ**まるごと**アップロードします。
   **必ずバイナリモード**で送ってください（テキストモードだと中身が変わって照合に失敗します）。
4. 使う人の側は、右クリックメニューの「ネットワーク更新」で新しくなります。
   ゴーストから始めたいときは「**ネットワーク更新をする**」ブロックを置きます。

> `updates2.dau` の形式は公式には公開されていません。なしスタジオは、公開されている
> 読み取り側の実装（ninix-kagari の `lib/ninix/update.rb`）に合わせて書いています。
> `md5 miss` などでうまくいかないときは、**アップロードするフォルダを SSP のウィンドウに
> ドラッグ＆ドロップ**すると SSP が作り直してくれるので、それを上書きしてください。
> `.nar` の中には入れていません（アーカイブでは無くてもかまわないためです）。

更新のようすは `OnUpdateBegin` / `OnUpdateReady` / `OnUpdateComplete` / `OnUpdateFailure`
のイベントで受け取れます。ブロックを書かなくても、**更新できたとき**と**失敗したとき**は
栞が一言いいます（「変わりなし」と途中経過は黙っています）。

> 消したいファイルがあるときは、置き場所に `delete.txt` を用意します
> （ネットワーク更新は上書きだけで、消す操作はしないためです）。

### 保存される場所

`nashi-studio.exe` と同じフォルダに作られます。

| | |
|---|---|
| `projects\` | プロジェクト（作りかけのブロック）。初回起動時にサンプルが入ります |
| `output\` | 書き出したゴースト（書き出し先を変えていない場合） |
| `nashi-studio.json` | 最後に開いたプロジェクト・書き出し先・ウィンドウの大きさ |
| `webview-data\` | WebView2 の作業フォルダ（消しても再生成されます） |

exe のとなりに `nashi.dll` を置くと、埋め込みのものより **そちらが優先** されます（栞を作り直したときに便利）。

## ビルド

Visual Studio の「C++ によるデスクトップ開発」が入っていれば、これだけです。

```powershell
.\build.ps1            # 栞(32bit DLL) → スタジオ(64bit EXE)
.\build.ps1 -Test      # 画面を出さずに動かすコンソールも作り、テストも走らせる
.\build.ps1 -Release   # きれいに作り直してテストし、配布用の zip を作る
```

`-Release` は `dist\nashi-studio-<版>.zip` を作ります（中身は exe と読みもの）。
版の数字は **ルートの `VERSION` ファイル**の 1 行だけです。ここを直すと、
zip の名前と exe のプロパティ（右クリック→プロパティ→詳細）の両方に入ります。
変わったことは `CHANGELOG.md` に足してください。

`-Test` を付けると、7 つのテストが走ります。

| | |
|---|---|
| **そろい点検**（`tools\check-blocks.js`） | ブロックが「定義・栞・説明・テスト」のすべてにそろっているか。ビルドが要らないので、いちばん先に走ります |
| **一致テスト**（`shiori\test\parity\parity.js`） | 同じ `interp.cpp` を **32bit（SSP に入る栞）** と **64bit（なしスタジオの「ためす」）** で組んで、同じ `ghost.json` を流し、出てきたさくらスクリプトが一致するか見くらべます（ビット幅に頼った書きかたを見つけます） |
| **ふるまいテスト**（`shiori\test\behavior\behavior.js`） | 栞だけが持っている判断 — 同じイベントに複数あるときどれを選ぶか、ブロックが無いときの既定の反応、`OnClose` の `\-`、「◯秒ごと」の間引き、なでなでの生成、通信の届け先、SAORI（テスト用のおそい DLL を実際に呼びます） — が期待どおりか |
| **書き出しテスト**（`studio\test\export.js`） | 書き出したファイル（`surfaces.txt` / `descript.txt` / `ghost.json` / `install.txt`）の中身が期待どおりか。`updates2.dau` は MD5 を node の `crypto` と突き合わせます |
| **エディタテスト**（`ui\test\editor.js`） | 読みこんだプロジェクトの整形（`model.js`）と、チェックタブが出す注意（`lint.js`）が期待どおりか |
| **輸入の点検**（`tools\check-imports.js`） | 出来あがった `nashi.dll` の輸入表を直に読んで、**Windows 2000 に無い API** が混ざっていないか。混ざると、そこから下の Windows ではDLL の読みこみ自体が失敗します |
| **画面ファイルの点検**（`ui\test\modules.js`） | `ui\js\*.js` を `index.html` と同じ順に読みこんで、落ちないか・`N.Xxx.yyy()` の呼び先がそろっているか。ファイルを分けたときの**移し忘れ**を捕まえます |

この 7 つだけ **Node.js** を使います（入っていなければ飛ばします。アプリの動作には要りません）。
ふるまいテストには、わざと待つ場面（おそい SAORI と終了が重なるところ）があるので、
10 秒ほどかかります。
ブロックやふるまいを足したら、`shiori\test\` `studio\test\` `ui\test\` の材料と期待値も
いっしょに直してください。書き出しかたをわざと変えたときは、出てきたものを目で確かめてから
`node studio\test\export.js --update` で期待値を作りなおします。

**ブロックを 1 つ足すときの手順**（どのファイルに何を書くか）と、つまずきやすいところは
[`docs/maintenance.md`](docs/maintenance.md) にまとめてあります。

この 7 つは **GitHub でも自動で走ります**（`main` への push・`v*` タグ・プルリク）。
打ち忘れても止まるようにするためのものです。設定は `.github/workflows/build.yml`。

個別に作るときは `shiori\build.ps1` / `studio\build.ps1`。
スタジオのビルドでは `studio\tools\embed.ps1` が `ui\` 以下と `nashi.dll` を
リソースにまとめ、exe に埋め込みます（UI を直したら再ビルドしてください）。

WebView2 の SDK は `studio\third_party\webview2\` に入れてあります（ヘッダと静的リンク用の
`WebView2LoaderStatic.lib` だけ。MIT ライセンス）。ダウンロードは不要です。

### スマートアプリコントロールでブロックされたら

Windows 11 の **スマートアプリコントロール**（既定でオンの環境があります）は、
署名がなく実績のない exe をブロックすることがあります。ビルドしたばかりの
`nashi-studio.exe` が「アプリケーション制御ポリシーによってブロックされました」と
言われた場合は、次のどれかで対応してください。

1. **少し待ってもう一度実行する** — 判定が確定すると通ることがあります（確実ではありません）。
2. **コード署名する** — 公的な認証局のコード署名証明書があれば確実です。
   ```powershell
   .\studio\build.ps1 -SignThumbprint <証明書の拇印>
   ```
   自己署名証明書ではスマートアプリコントロールの信頼は得られません。
3. **スマートアプリコントロールを切る** — Windows セキュリティ →「アプリとブラウザーの制御」→
   「スマートアプリコントロール」→ オフ。
   **一度オフにすると Windows を再インストールするまで戻せません**。よく考えてから行ってください。

作りたての `nashi.dll` や `test_host.exe` が、テストの途中で同じように止められることも
あります（`error 4551`）。**もう一度ビルドすると通る**ことが多いです。

## 栞のしくみ

エディタの「ためす」も、**この栞そのもの**が動かしています。なしスタジオは
`shiori/src/interp.cpp` を 64bit で組んだものを積んでいて、画面は `POST /api/preview`
で頼むだけです（画面側にブロックの解釈はありません）。
違うのは 2 つだけで、**SAORI は呼びません**（本物の 32bit DLL が要るため）、
**時計や起動回数は画面から渡します**。それ以外は SSP に入れたときと同じ答えになります。

* SHIORI/3.0 の DLL として `load` / `unload` / `request` を公開しています（`src/nashi.def`）。
* 起動時に、DLL と同じフォルダの **`ghost.json`** を読み込みます。
* SSP から来たイベント（`OnBoot`、`OnMouseDoubleClick` など）に対応するブロックを実行し、
  結果のさくらスクリプトを `Value:` で返します。
* 同じイベントのスクリプトが複数あるときは、`weight`（えらばれやすさ）で抽選します。
* `OnSecondChange` を数えて、設定した間隔で **ランダムトーク**（`kind: "talk"`）を再生します。
  直近に出したトークは候補から外すので、同じ話が続きません（外す数はゴーストの設定で変えられます。
  既定はトーク数の半分・最大 8）。出した順番は `nashi_save.json` に残ります。
* 同じイベントにブロックが複数あるときも、直前に選んだものは避けます。
* 変数は終了時（および 2 分ごと）に **`nashi_save.json`** へ保存され、次回起動時に復元されます。
* リクエストが Shift_JIS で来ても UTF-8 に変換して処理し、応答は常に UTF-8 で返します。
* イベントは大きく **はじめの1回**（`OnFirstBoot` / `OnBoot`）・**定常ループ**（`OnSecondChange`）・
  **その他のイベント**の 3 つに分かれます。定常ループは SSP が毎秒たたいてくるので、
  帽子ブロックの「◯秒ごと」で間引けます（`everySec`）。
* マウス系のイベントは、**当たった場所（あたま・かお・むね・スカート・て）と相手**で
  しぼり込めます。書き出す仮シェルにも、その名前の当たり判定を入れてあります。
* `OnMouseMove` が同じ場所で続いたら **`OnNadeNade`（なでられたとき）** を自分で作ります。
  SSP にはこのイベントはありません。栞の中で数えています。
* **ゴースト間通信**（`OnCommunicate`）に対応しています。相手の名前と言われたことで
  しぼり込めます。こちらから話しかけるときは応答に `Reference0: 相手の名前` を付けます。
  話しかけ合いが 8 往復続いたら、しゃべるだけにして通信は打ち切ります。
* **外部モジュール（SAORI）** は読み込んだまま持ち、終了時にまとめて解放します。
  「答えを待たない呼び出し」は別のスレッドで動きますが、DLL をつつくのは**ひとつずつ**で、
  届いた答えを変数に入れるのは**主スレッドだけ**です（同時に触らないようにしています）。
  答えが届くと、つぎの `OnSecondChange` で `OnSaoriDone` を作って知らせます。
* しぼり込みを書いたブロックは、条件なしの同じイベントより**優先**されます。
* ブロックが未定義のイベントには、あいさつなどの控えめな既定動作を返します。
  `OnClose` では必ず `\-` を付けて、ゴーストがちゃんと終了するようにします。

### SSP なしで試す

```powershell
.\build.ps1 -Test
.\shiori\dist\test_host.exe .\output\なしちゃん\ghost\master OnBoot OnMouseDoubleClick:0,0,0,0,Head OnClose
```

`イベント名:参照0,参照1,...` の形で指定します。`OnSecondChange:0,1*200` のように `*回数` を付けると繰り返せます。
`!sleep:300` を挟むと、その場で 300 ミリ秒待ちます（答えを待たない SAORI のように、
裏で動いているものが終わるのを待つとき用）。

## つくれるもの / まだできないこと

できること:

* セリフ、表情（サーフェス）切り替え、間（ウェイト）、クリック待ち、バルーン切り替え
* 選択肢（`\q`）とその行き先、リンク（`\_a`）、音（`\_v`）
* 変数（好感度・フラグなど）、条件分岐、くりかえし、ランダム分岐、トークの呼び出し
* ゴースト間通信（`OnCommunicate`）— 話しかけられたときの反応と、こちらから話しかけること
* 3 人目以降のキャラ（`\p[n]`）の切りかえ
* 外部モジュール（**SAORI**）の呼び出し — ゴーストのフォルダに置いた 32bit の DLL
  （答えを待たずに呼ぶこともできます。時間のかかる SAORI でも SSP が止まりません）
* **うごき**（SERIKO のアニメーション）— 立ち絵をパラパラ切りかえる。ゴーストタブで作る
  （こまごとに位置ずらし・重ねかた（`interpolate` や `blend-*` など）を選べます。
  ほかのうごきを動かす／止める、APNG を差しこむ、そのうごきの間だけ触れる
  当たり判定（四角・だ円・丸・多角形）を足す、もできます）
* **ネットワーク更新**（`homeurl`・`updates2.dau` の書き出し・更新のイベント・更新のブロック）
* **たずねる**（入力ボックス）— 使う人が書いた文字を、そのまま変数に入れる
* **N 秒後によぶ**（かんたんな予約）、**イベントを自分で起こす**、
  **交代する** / **ブラウザで開く**
* 仮のシェル（立ち絵）と、**バルーン（吹き出し）**の自動生成
* 時刻・曜日・起動回数・**いまごろ（朝昼夕夜）・季節**などの情報、四則演算・比較・文字列操作
* ランダムトークの**まとまり**（朝のトーク、季節のトーク…）と、そこから 1 つよぶブロック
* どうしても必要なときの「さくらスクリプトをそのまま出す」ブロック

まだできないこと（足しかたは [`docs/maintenance.md`](docs/maintenance.md) の「ブロックを 1 つ足す」にあります）:

* SERIKO の残り（`alternativestart` などのまとめ操作、`scaling` / `insert`、
  `blend-*` のこまかい種類、着せ替え（MAYUNA）の `bind`）

## 安全のはなし

* **ポートは開きません。** 画面からの要求は WebView2 の中で受け取り、そのまま exe の中で
  処理しています。外に出る通信は、SSP と話すときの `127.0.0.1:9801` だけです。
* 画面は `https://nashi.example/` という**見せかけのアドレス**で動いていて、
  そこから外のページへは移動しません（移動しようとしたら、既定のブラウザに渡します）。
  外部リンクを開くときも `http` / `https` だけを渡します。
* exe の中の API は、**画面自身から出た要求だけ**を受け付けます
  （独自ヘッダか、同じアドレスから来たことの確認）。
* 栞は、**外から来た文字**（他のゴーストに言われたこと、入力ボックスに書かれたもの）を
  さくらスクリプトに入れるとき、タグを閉じる `[` `]` と改行を落とします。
  ただし `さくらスクリプトをそのまま出す` ブロックは素通しなので、そこに外から来た文字を
  入れないでください。
* **人からもらったプロジェクト（.json）は、開く前に中身を確かめてください。**
  立ち絵の画像はパスで指定されているので、書き出すとその画像がゴーストに同梱されます。
  知らないパスが入っていたら、ゴーストタブの「立ち絵の画像」で外せます。
* 栞（`nashi.dll`）が読む SAORI の DLL は、ゴーストのフォルダの中だけです
  （`..` や絶対パスは受け付けません）。
* **待たない SAORI** が終わらないまま、ゴーストが終わることがあります。栞は 5 秒だけ待って、
  あとは置いていきます（そこで固まらないため）。置いていっても、走っているスレッドが
  消えたメモリや外れた栞を触らないように、置き場を分けあい、栞じしんを押さえています。
* 変数 1 つに入れておける長さは 32KB までです（つなげ続けてメモリを使いきらないため）。
  1 回に出すさくらスクリプトも 32KB までで、こえたぶんは出しません。

## メモ

* 生成される仮シェルは、絵を用意するまでの繋ぎです。配布するゴーストには自分の絵を使ってください。
* PNG も .nar も外部ライブラリを使わず自前で書き出しています（zlib 不要）。
* 画面は WebView2 の中で動く HTML/CSS/JS ですが、`https://nashi.example/` という
  見せかけのアドレスから exe の中身を直接返しているだけで、通信はしていません。
* `ui\index.html` をブラウザで直接開くと、画面の見た目は出ますが、保存・書き出し・
  「ためす」は動きません（どれも exe の中の処理を呼んでいるためです）。
